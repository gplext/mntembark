# System Architecture & Geographic Domain Model

This document outlines the architecture of **MNT Embark**, with a dedicated deep-dive into the geographic and merchandising taxonomy: **Countries**, **Locations**, and **Destinations**, their database relationships, and their implementation across the frontend and backend.

---

## 1. High-Level Architecture Overview

MNT Embark is structured as a pnpm monorepo consisting of:

* **Frontend (`artifacts/mnt-embark-web`)**:
  * React 18 single-page application built with Vite and Tailwind CSS.
  * Routing via `wouter`, state and API caching via `@tanstack/react-query`.
  * Component library and design tokens in `artifacts/mnt-embark`.
* **Backend (`artifacts/api-server`)**:
  * Express.js HTTP API server running on Node.js.
  * Cookie-based session authentication with role-based access control (Super Admin vs. Sub-Admin).
  * Auto-seeding and table initialization on server boot.
* **Database Layer (`lib/db`)**:
  * PostgreSQL 16 managed via Drizzle ORM.
  * Typed query helpers in `@workspace/db/queries` (`taxonomy.ts`).
* **API Contracts (`lib/api-spec` & `lib/api-zod`)**:
  * OpenAPI 3.1 specification (`openapi.yaml`).
  * Autogenerated Zod validation schemas and TypeScript types (`@workspace/api-zod`).
  * Autogenerated React Query hooks (`@workspace/api-client-react`).

## 2. Geographic & Merchandising Domain Model

A core architectural achievement of MNT Embark is separating **political geography** (where places are legally/geographically located) from **merchandising concepts** (the travel packages and curated experiences sold to guests).

### 2.1 The Three Core Entities

```
+-------------------------------------------------------------------------------+
|                                  DESTINATION                                  |
|         "East Africa", "Southeast Asia", "Patagonia", "Amalfi Coast"          |
|                   (Curated experiential travel concept)                       |
+-------------------------------------------------------------------------------+
            | M:N (destination_countries)           | M:N (destination_locations)
            v                                       v
+-----------------------+              +----------------------------------------+
|        COUNTRY        | <--- 1:N --- |                LOCATION                |
|   "Kenya", "Thailand" |              |     "Serengeti", "Bangkok", "Phuket"   |
|  (Sovereign State)    |              |       (Specific physical city/base)    |
+-----------------------+              +----------------------------------------+
            ^                                       ^
            | (derived)                             | 1:N (location_id)
            +----------------- TOURS ---------------+
                       (1:N via destination_id)
```

#### 1. `countries` (`countriesTable`)
* **Domain Meaning**: Real-world sovereign/political nations (e.g. *Thailand*, *Kenya*, *Italy*, *Iceland*).
* **Database Columns**:
  * `id`: Serial Primary Key.
  * `slug`: Unique slug for URL routing (e.g. `thailand`, `kenya`).
  * `name`: Display name (e.g. `Thailand`).
  * `code`: Standard ISO 3166-1 alpha-2 code (e.g. `TH`, `KE`, `IT`).
  * `latitude`: Real geographic coordinate (-90 to 90), auto-populated with country centroid upon creation.
  * `longitude`: Real geographic coordinate (-180 to 180), auto-populated with country centroid upon creation.
  * `image`: Cover photo or custom icon used directly on interactive map pins.
  * `description`, `display_order`, `created_at`.
* **Why this exists**: Eliminates unstandardized free-text country strings (e.g. preventing "UAE", "U.A.E.", and "United Arab Emirates" from being treated as three unrelated entities). ISO codes allow flags, currencies, and visa guidelines to be wired deterministically. Accurate coordinates empower dynamic map projection without hardcoded lookup tables.

#### 2. `locations` (`locationsTable`)
* **Domain Meaning**: Granular, physical launch bases or cities visited by a tour (e.g. *Bangkok*, *Phuket*, *Malé*, *Serengeti*).
* **Database Columns**:
  * `id`: Serial Primary Key.
  * `slug`: Unique slug (e.g. `bangkok`, `serengeti`).
  * `name`: Display name (e.g. `Bangkok`).
  * `country_id`: Foreign key referencing `countries.id` (`ON DELETE SET NULL`).
  * `image`, `description`, `display_order`, `created_at`.
* **Relationship to Country**: Strict **Many-to-One (1:N)**. A city or base belongs to exactly one sovereign country.

#### 3. `destinations` (`destinationsTable`)
* **Domain Meaning**: The curated marketing concept sold to the traveler (e.g. *"Southeast Asia"*, *"The Amalfi Coast"*, *"East Africa"*, *"The Silk Road"*).
* **Why it is distinct from Country/Location**: A destination concept is not bound to a single country's political borders. *East Africa* spans Kenya, Tanzania, Uganda, and Rwanda; *Patagonia* spans Chile and Argentina.
* **Database Columns**:
  * `id`: Serial Primary Key.
  * `slug`: Unique slug (e.g. `southeast-asia`, `patagonia`).
  * `name`: Curated title (e.g. `Southeast Asia`).
  * `cover_image`: Hero image representing the experience.
  * `display_order`, `created_at`.
  * Legacy nullable columns (`country`, `region`, `description`) retained for backward compatibility.

---

### 2.2 Join Tables (Many-to-Many Relationships)

To model how a destination concept relates to political geography, two explicit join tables are used:

1. **`destination_countries` (`destinationCountriesTable`)**:
   * Columns: `destination_id` (FK), `country_id` (FK), `display_order`.
   * Composite Primary Key: `(destination_id, country_id)`.
   * Defines which sovereign countries comprise a curated destination.
2. **`destination_locations` (`destinationLocationsTable`)**:
   * Columns: `destination_id` (FK), `location_id` (FK), `display_order`.
   * Composite Primary Key: `(destination_id, location_id)`.
   * Defines which specific cities or bases are highlighted under that destination.

---

### 2.3 How Tours Link to Geography

In `toursTable`:
* **`destination_id`** (`integer` FK -> `destinations.id`):
  * The primary destination under which the tour is merchandised and cataloged.
  * Drives primary URL hierarchy, breadcrumbs, and high-level grouping.
* **`location_id`** (`integer` FK -> `locations.id`):
  * The physical home base or departure city for the itinerary.
* **Country is Derived, Never Duplicated**:
  * A tour does not store a redundant `country_id` column.
  * Instead, country is resolved through `tours.location_id -> locations.country_id -> countries.name / slug`.
  * This guarantees database consistency: it is impossible for a tour to be assigned to city "Bangkok" and country "Kenya".

```sql
-- Standard tour place projection used by selectToursWithPlace()
SELECT 
  tours.*,
  locations.id AS "locationId",
  locations.name AS "locationName",
  countries.name AS "countryName"
FROM tours
LEFT JOIN locations ON locations.id = tours.location_id
LEFT JOIN countries ON countries.id = locations.country_id;
```

## 3. Usage in the Application

### 3.1 Destinations Page (`/destinations`)

The Destinations page offers two main views of the destination catalog:

1. **Illustrated World Map (`DestinationsMap.tsx`)**:
   * Renders Natural Earth equirectangular geo-topology on a standardized `1200 × 580` canvas.
   * **Equirectangular Projection**:
     $$x = \frac{\text{lng} + 180}{360} \times 1200, \quad y = \frac{90 - \text{lat}}{180} \times 580$$
   * **Inversion for Visual Pin Positioning**:
     $$\text{lng} = \frac{x}{1200} \times 360 - 180, \quad \text{lat} = 90 - \frac{y}{580} \times 180$$
   * **Dynamic Pin Resolution**:
     * Resolves coordinates directly from database `latitude` and `longitude`.
     * If unassigned, automatically resolves the geographic centroid from standard ISO dictionaries (`COUNTRY_DEFAULT_COORDINATES`).
   * **Custom Country Icon / Image on Map Pin**:
     * If the country or destination has an image or icon configured, it is rendered directly inside the circular pin disc with a gold bezel and high-res SVG clipPath.
     * If no image is uploaded, it displays the ISO country code or terrain category icon.
   * **Interactive Tooltips & Navigation**:
     * Hovering a pin displays active tours and country metadata with radar pulse effects.
     * Clicking a pin routes directly to `/tours?destinationSlug={slug}` or `/tours?countrySlug={slug}`.
2. **Destination Cards Grid (`DestinationsPage`)**:
   * Lists all active destinations.
   * Each card displays the destination's `name`, `coverImage`, and geographic subtitle (`country · region`).
   * On card hover, dynamic previews show up to 3 tours belonging to that destination.
   * Clicking a card opens `/tours?destinationSlug={slug}`.

### 3.2 Tours Page (`/tours` & `/tours/:slug`)

#### Cascading Taxonomy Filtering (`TourFilterSidebar.tsx`)
The filter sidebar implements progressive cascading place filters:

1. **Destination Filter**:
   * User selects a destination (e.g. *Patagonia*).
   * App invokes `GET /api/destinations/{slug}/places`, fetching:
     * `countries`: Countries linked via `destination_countries`.
     * `locations`: Cities linked via `destination_locations`.
2. **Country Filter (Dependent)**:
   * Enabled once a Destination is active.
   * Selecting a country automatically filters the visible locations in the next dropdown to only those belonging to that country (`loc.countrySlug === countrySlug`).
3. **Location Filter (Dependent)**:
   * Filters the tours to the exact city/base.
4. **URL Synchronization**:
   * All selections are bound to search params (`?destinationSlug=...&countrySlug=...&locationSlug=...`), allowing filtered views to be shared and bookmarked.

#### Tour Card Place Formatting (`TourCard.tsx`)
* The `tourPlace(tour)` helper checks `tour.locationName` and `tour.countryName`.
* If found, it renders `"Bangkok, Thailand"` or `"Serengeti, Tanzania"`.
* If names are identical (e.g. Location "Iceland", Country "Iceland"), it deduplicates to `"Iceland"`.
* Falls back gracefully to legacy text `tour.location` if relational place IDs are absent.

#### Tour Detail View (`/tours/:slug`)
* Fetches the full taxonomy tree using `getTourWithTaxonomy(slug)`.
* Resolves `tour.destination`, `tour.location`, and `tour.location.country` in a single query.
* Displays location and duration badges on the itinerary sidebar.

### 3.3 Admin Portal Management

1. **Destinations, Countries & Locations (`/admin/destinations`)**:
   * Dedicated multi-tab management interface for:
     * **Destinations**: Create and edit destination concepts, hero images, and assign many-to-many countries and locations.
     * **Countries**: Manage sovereign countries, slugs, and ISO codes.
     * **Locations**: Manage cities, hero images, and associate each location with its parent country.
2. **Tour Management (`/admin/tours`)**:
   * Allows setting both:
     * **Destination** (curated marketing category).
     * **Location (Structured)** (city and associated country).
